# برنامه‌ی یک‌هفته‌ای پروژه‌ی فروش بلیط سینما (FastAPI + Postgres + Redis)

هدف نهایی: یه پروژه‌ی کامل، مستند، و قابل دفاع رو گیت‌هاب که هم مهارت طراحی دیتابیس رو نشون بده، هم درک درست از مسائل مهندسی نرم‌افزار (consistency، concurrency، queue، پرداخت).

---

## روز ۱ — پایه‌ریزی + طراحی دیتابیس (سنگین‌ترین روز از نظر فکری)

### صبح (۲-۳ ساعت): آماده‌سازی محیط
- [ ] نصب Docker Desktop و تست با `docker run hello-world`
- [ ] نوشتن `docker-compose.yml` برای Postgres و Redis
- [ ] `docker compose up -d` و تست اتصال با یه ابزار مثل DBeaver یا psql به Postgres، و `redis-cli ping` به Redis
- [ ] ساخت virtual environment پایتون و نصب پکیج‌های اولیه (fastapi, uvicorn, sqlalchemy, asyncpg, alembic, redis, pydantic-settings)
- [ ] یه اسکلت خیلی ساده‌ی FastAPI با یه endpoint تست `/health` که وضعیت اتصال به هر دو دیتابیس رو برگردونه

### ریسرچ (۳۰-۴۵ دقیقه)
- [ ] خوندن مقاله‌ی "Solving Double Booking at Scale" (راه‌حل Ticketmaster/BookMyShow/Airbnb)
- [ ] نگاه به caseهای طراحی سیستم بلیط سینما (repo grokking-the-object-oriented-design-interview)
- [ ] یادداشت: هر شرکت چه تصمیمی گرفته و چرا (برای استفاده در توجیه تصمیم‌های خودت)

### بعدازظهر/شب (۲-۳ ساعت): طراحی ERD
- [ ] لیست کامل موجودیت‌ها (entities):
  - `Cinema` (سینما)
  - `Hall` (سالن نمایش، متعلق به یک سینما)
  - `Seat` (صندلی فیزیکی، متعلق به یک سالن - ردیف، شماره، نوع: معمولی/VIP/کاناپه‌ای)
  - `Movie` (فیلم)
  - `Showtime` (سانس = فیلم + سالن + زمان شروع)
  - `ShowtimeSeat` (وضعیت هر صندلی برای یک سانس خاص: available/held/booked + قیمت)
  - `User` (نقش‌ها: customer, theater_manager, admin)
  - `Booking` (رزرو نهایی یک کاربر)
  - `BookingSeat` (رابطه‌ی بین یک رزرو و صندلی‌های انتخاب‌شده)
  - `Payment` (وضعیت پرداخت هر رزرو)
  - `Ticket` (بلیط نهایی بعد از موفقیت پرداخت، شامل QR code)
- [ ] تصمیم کلیدی: چرا `Seat` (فیزیکی) از `ShowtimeSeat` (وضعیت per-showtime) جداست؟ این تصمیم رو برای خودت بنویس چون دقیقاً سوال مصاحبه‌ست
- [ ] تعریف `UNIQUE(showtime_id, seat_id)` روی جدول `booking_seat` - این قلب تضمین consistency پروژه‌ست
- [ ] رسم دیاگرام (با من، یا با ابزاری مثل dbdiagram.io)
- [ ] نوشتن مدل‌های SQLAlchemy مطابق دیاگرام
- [ ] اولین Alembic migration و اجرای موفق

**خروجی امروز:** پروژه بالا میاد، به هر دو دیتابیس وصله، جدول‌های اصلی ساخته شدن.

> **آپدیت برنامه:** روز ۱ کامل انجام شد (طبق تسک‌های بالا، به‌علاوه‌ی چندتا مورد اضافه: init/push گیت‌هاب، اجرای واقعی schema.sql روی cinema_db، تست زنده‌ی چرخه‌ی consistency با داده‌ی واقعی، و رسم ERD تصویری). از اینجا به بعد، کار فنی اصلی تو ۳ روز (۲ تا ۴) جمع شده تا ۳ روز آخر (۵ تا ۷) کامل برای مرور، مستندسازی و آماده‌سازی دفاع باشه. بخش ریسرچ هم از تسک‌های روزانه جدا شده و پایین همین فایل، تو یه بخش مستقل اومده.

## روز ۲ — لایه‌ی ادمین + مدل‌ها/مایگریشن + یادگیری Redis + seat hold

### بلوک ۱ (صبح): از schema.sql به مدل‌های واقعی
- [ ] نوشتن مدل‌های SQLAlchemy مطابق `schema.sql` (شامل نگاشت دستی partial unique index با `Index(..., postgresql_where=...)`، چون SQLAlchemy این رو خودکار از روی مدل نمی‌سازه)
- [ ] اولین Alembic migration، و مقایسه‌ش با `schema.sql` (باید دقیقاً همون چیزی رو بسازه که دستی نوشتی)
- [ ] Pydantic schemas برای هر موجودیت (Create/Read/Update جدا - مثل DTO تو دات‌نت)
- [ ] Repository pattern برای دسترسی به دیتابیس (لایه‌ی جدا، نه مستقیم تو router)

### بلوک ۲ (بعدازظهر): CRUD ادمین
- [ ] endpoint های CRUD: سینما، سالن + چیدمان صندلی، فیلم، سانس
- [ ] موقع ساخت سانس: چک تداخل زمانی دو سانس تو یه سالن (در سطح اپلیکیشن؛ نسخه‌ی exclusion constraint دیتابیسی رو گذاشتیم برای روز ۶ اگه وقت اومد)
- [ ] موقع ساخت سانس: ساخت خودکار یه `ShowtimeSeat` با وضعیت `available` به‌ازای هر صندلی فیزیکی سالن
- [ ] احراز هویت JWT + تفکیک نقش (admin / theater_manager با `CinemaManager` / customer)

### بلوک ۳ (شب): یادگیری متمرکز Redis + پیاده‌سازی seat hold
- [ ] یادگیری فشرده‌ی Redis (لیست منابع تو بخش ریسرچ پایین فایل) - فقط همون مفاهیمی که لازم داری: TTL/expiry، `SET NX EX`، sorted set
- [ ] endpoint انتخاب صندلی: `seat_hold:{showtime_id}:{seat_id}` با `SET NX EX`
- [ ] endpoint نمایش وضعیت صندلی‌های یک سانس (ترکیب Postgres + Redis)
- [ ] endpoint آزادسازی دستی hold

**خروجی امروز:** ادمین کامل کار می‌کنه، پروژه به‌جای schema خام، مدل و migration واقعی داره، و دو کاربر همزمان نمی‌تونن یه صندلی رو انتخاب کنن.

## روز ۳ — تضمین نهایی consistency + پرداخت sandbox + بلیط

### بلوک ۱ (صبح): قفل نهایی و تست concurrency
- [ ] تراکنش نهایی رزرو (طبق چیزی که با هم نوشتیم): پرداخت موفق → یک تراکنش شامل insert به `booking_seat` + آپدیت `showtime_seat.status = 'booked'`
- [ ] تراکنش کنسل رزرو (همون pseudocode که آماده‌ست) → پیاده‌سازی واقعی‌ش
- [ ] مدیریت خطای duplicate roll: پیام درست به کاربر، نه ۵۰۰ خام

### بلوک ۲ (صبح/ظهر): تست رسمی concurrency (جدی بگیرش، دقیقاً همینو تو مصاحبه می‌پرسن)
- [ ] تبدیل تست دستی به یه تست pytest با asyncio که چند request همزمان به یه صندلی می‌زنه
- [ ] اثبات و ثبت نتیجه (برای README روز ۵)

### بلوک ۳ (بعدازظهر): پرداخت sandbox
- [ ] payment provider ساختگی (endpoint با نتیجه‌ی قابل کنترل موفق/ناموفق)
- [ ] state machine: `pending -> processing -> succeeded/failed -> refunded`
- [ ] `idempotency_key` برای جلوگیری از پرداخت تکراری
- [ ] background worker (arq، ساده‌تر از Celery برای پروژه‌ی یک‌نفره) برای تایید پرداخت

### بلوک ۴ (شب): صدور بلیط
- [ ] وقتی پرداخت موفق شد: `booking` به confirmed، `ticket` با QR code یکتا ساخته بشه
- [ ] مدیریت timeout: اگه پرداخت کامل نشد، انقضای TTL خود Redis صندلی رو آزاد می‌کنه (نیازی به cleanup دستی نیست)

**خروجی امروز:** می‌تونی با اطمینان بگی «double booking غیرممکنه» و اثباتش کنی، و کل فلوی انتخاب صندلی تا بلیط نهایی کار می‌کنه.

## روز ۴ — صف مدیریت ازدحام + آمار + جمع‌بندی فنی

### بلوک ۱ (صبح): صف انتظار (استفاده‌ی دوم و خلاقانه از Redis)
- [ ] برای سانس‌های پرطرفدار: کاربر وارد یه sorted set تو Redis می‌شه (امتیاز = زمان ورود)
- [ ] admit کردن N نفر اول صف در هر بازه‌ی زمانی، با توکن موقت برای رفتن به مرحله‌ی انتخاب صندلی
- [ ] endpoint نمایش جایگاه کاربر تو صف

### بلوک ۲ (بعدازظهر): آمار برای مدیر/ادمین
- [ ] گزارش فروش (هر سانس/فیلم/سینما) با aggregate query
- [ ] درصد پرشدگی سالن (occupancy rate) با window function
- [ ] (اختیاری اگه وقت اومد) exclusion constraint دیتابیسی برای جلوگیری از تداخل سانس‌ها + materialized view برای گزارش سنگین‌تر

### بلوک ۳ (شب): جمع‌بندی فنی
- [ ] تست‌های واحد برای منطق اصلی باقی‌مونده (محاسبه‌ی قیمت، state machine پرداخت)
- [ ] یه مرور سریع رو کل کدبیس: هرجایی که TODO یا کد نیمه‌کاره مونده رو یا تموم کن یا آگاهانه برای بعد از دفاع بذار

**خروجی امروز:** بخش فنی پروژه تمومه. از اینجا به بعد دیگه فیچر جدید اضافه نمی‌کنیم، فقط مستندسازی، مرور، و آماده‌سازی داریم.

## روز ۵ — مستندسازی کامل (README)

- [ ] بخش معرفی و معماری کلی + جای‌گذاری ERD تصویری
- [ ] بخش «چرا این تصمیم‌ها؟» (مهم‌ترین بخش README برای مصاحبه):
  - چرا `ShowtimeSeat` جدا از `Seat`
  - چرا `price_snapshot` به‌جای لینک مستقیم به `seat_type`

  - چرا `held` فقط تو Redisه، نه تو Postgres
  - چرا partial unique index رو `booking_seat` (و باگی که قبلش بود)
  - چرا `CinemaManager` برای دسترسی سطح-ردیف
  - چرا background worker برای پرداخت
- [ ] بخش «چطور تستش کردم» - نتیجه‌ی تست concurrency + تست دستی چرخه‌ی claim/cancel/reclaim

- [ ] پاک‌سازی و مرتب کردن تاریخچه‌ی commit ها اگه لازمه (پیام‌های commit واضح، مخصوصاً همون fix باگ partial index)

**خروجی امروز:** یه README که به‌تنهایی می‌تونه بخش زیادی از دفاع رو جلو ببره.

## روز ۶ — مرور عمیق و تسلط کامل رو پروژه

- [ ] مرور خط‌به‌خط کل کدبیس، نه برای تغییر، برای این‌که مطمئن بشی هر خط رو می‌تونی توضیح بدی
- [ ] برای هر تصمیم مهم (لیست بالا)، بلند توضیحش بده انگار داری به یه نفر دیگه یاد می‌دی - اگه گیر کردی جایی، دقیقاً همونجا رو باید بیشتر مرور کنی
- [ ] رفع هر بخش ناتمیز یا گیج‌کننده‌ی کد که موقع مرور پیدا می‌کنی
- [ ] اگه وقت اضافه اومد: یکی از موارد اختیاری (exclusion constraint، materialized view) رو تکمیل کن

**خروجی امروز:** پروژه رو مثل چیزی که خودت از اول تا آخر ساختی می‌شناسی، نه چیزی که فقط یه بار پیاده‌ش کردی.

## روز ۷ — آماده‌سازی نهایی دفاع

- [ ] نوشتن یه اسکریپت کوتاه دمو (مثلاً: ساخت سینما → تعریف سانس → claim صندلی → دمو زنده‌ی رد شدن booking دوم → کنسل → claim دوباره → پرداخت → بلیط → آمار)
- [ ] لیست سوالات احتمالی مصاحبه + جواب کوتاه هرکدوم:
  - «اگه دو نفر همزمان یه صندلی رو بخوان چی می‌شه؟»
  - «اگه Redis از دسترس خارج بشه چی؟» (fallback به قفل خود Postgres)
  - «چطور مطمئنی پرداخت دوبار انجام نمی‌شه؟»
  - «چرا Postgres و نه NoSQL؟»
  - «چرا partial unique index به‌جای UNIQUE ساده؟» (همون باگی که پیدا کردی)
- [ ] یه دفاع آزمایشی: برای خودت (یا یه دوست) کل پروژه رو از اول تعریف کن، زمان بگیر
- [ ] مرور نهایی ریپو: README، ساختار پوشه‌ها، commit history، همه چیز مرتب و آماده

**خروجی امروز:** پروژه کامل، مستند، تمرین‌شده، آماده‌ی دفاع.

## بخش ریسرچ (مستقل از تسک‌های فنی روزانه)

این‌ها جدا از برنامه‌ی روزانه‌ان؛ هر وقت وقت آزاد داشتی (بین کارها، شب‌ها، یا یه بلوک مشخص) بهشون سر بزن. ترتیب پیشنهادی داره ولی اجباری نیست:

**قبل از روز ۲ (برای Redis):**

**درباره‌ی الگوی double booking (بخشی از این رو با مقاله‌ای که آوردی شروع کردیم):**
- [ ] تکمیل خوندن مقاله‌ی «Solving Double Booking at Scale» و مقایسه‌ی ۶ رویکردش با تصمیم نهایی خودمون
- [ ] repo `grokking-the-object-oriented-design-interview` (کیس طراحی سیستم بلیط سینما)
